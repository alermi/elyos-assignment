Voice SDKs in 10 minutes

Deepgram (speech to text) and ElevenLabs (text to speech) for the Elyos onsite, mapped onto the chat CLI you already built.

The short version

  • Deepgram is the ears. A WebSocket you push raw audio into. It pushes JSON transcripts back: quick guesses first, then final text.
  • ElevenLabs is the mouth. One HTTP request with text. Audio bytes stream back while the speech is still being generated.
  • ffmpeg is the plumbing. Node can't open a microphone or a speaker by itself. ffmpeg records the mic as raw audio for Deepgram, and ffplay (which comes with ffmpeg) plays what ElevenLabs sends back.
  • Your machine: both SDKs are installed, and npm run stt and npm run tts both work end to end with your keys.

2. Why you were asked to install ffmpeg 1 min

Node has no built-in microphone or speaker access. ffmpeg is the usual command-line tool for both, and it is what the SDKs' own helpers expect:

  • ElevenLabs playback. The SDK's play(audio) helper spawns ffplay and fails with "ffplay from ffmpeg not found" if it's missing. Its stream(audio) helper spawns mpv instead. The README says the SDK "requires MPV and ffmpeg to play audio".
  • Mic capture for Deepgram. ffmpeg -f dshow -i audio="Microphone Array (Realtek(R) Audio)" -f s16le -ar 16000 -ac 1 - writes raw PCM to stdout, and each chunk goes straight into connection.sendMedia(chunk). On a Mac it's -f avfoundation -i ":0", on Linux -f pulse -i default.
  • Test audio without talking. ffmpeg converts any file or URL into the format Deepgram expects, and -re plays it at real-time speed so it behaves like a live caller. Your build can even speak a test sentence itself (-f lavfi -i flite=text='...'). That's what npm run stt does by default.

The Python link. The Deepgram page in the brief is a 2022 Python "starter kit". It pins aiohttp==3.7.4.post0, which only has wheels for Python 3.6 to 3.9, so it won't pip install on your Python 3.11. Its mock server also uses pydub, which itself relies on ffmpeg. playground/stt.ts does the same job (file, URL or mic streamed to Deepgram) with the official TypeScript SDK.

3. Deepgram live speech-to-text 3 min

Package @deepgram/sdk 5.13. Version 5 changed the API: tutorials that use createClient() or LiveTranscriptionEvents describe v3 and v4.

import { DeepgramClient } from "@deepgram/sdk";

const deepgram = new DeepgramClient({ apiKey: process.env.DEEPGRAM_API_KEY });
const connection = await deepgram.listen.v1.connect({
    model: "nova-3",
    encoding: "linear16",       // raw audio has no header, so say what it is
    sample_rate: 16000,
    channels: 1,
    interim_results: "true",    // v5 takes these flags as strings
    endpointing: 300,           // ms of silence before speech_final
    utterance_end_ms: 1000,     // end-of-utterance from gaps between words
    vad_events: "true",         // SpeechStarted, the cue for barge-in
});

connection.on("message", (message) => { /* see the table below */ });
connection.connect();               // v5 sockets start closed
await connection.waitForOpen();     // a bad key rejects here with a 401, in ~150 ms

for await (const chunk of ffmpeg.stdout) connection.sendMedia(chunk);
connection.sendCloseStream({ type: "CloseStream" }); // send the last results, then close

The messages you get back

MessageMeaningWhat to do with it
Results, is_final: falseInterim guess. It will be revised.Live captions only.
Results, is_final: trueThis piece of text won't change.Append it to the current utterance.
Results, speech_final: trueA pause of at least endpointing ms was heard.The utterance is complete. Send the buffer to the LLM.
UtteranceEndNo new words for utterance_end_ms.Backup end signal for when background noise stops speech_final from firing.
SpeechStartedVoice activity started.Barge-in: stop the agent talking.
MetadataSent on close, includes request_id.Logs and support tickets.

A long sentence arrives as several is_final pieces before speech_final. So buffer the pieces and don't treat speech_final as the whole transcript. stt.ts does exactly this and prints a >>> utterance line.

Measured on your machine (nova-3, synthesized sample): interim results arrived about once a second, each 0.2 to 0.37 s after its last word was spoken. The final result came about 0.34 s after speech ended, most of which is the 300 ms endpointing wait.

Gotchas worth saying out loud

  • Silence kills the socket. If no audio arrives for 10 s, Deepgram closes the connection (NET-0001). If you pause the mic, for example while the agent speaks, call sendKeepAlive({ type: "KeepAlive" }) every 3 to 5 s.
  • The format must match. encoding and sample_rate have to describe what ffmpeg actually produces. Wrong values give empty or garbled transcripts, not an error. For WAV or MP3 (audio with a header), leave both out.
  • Graceful close vs hard stop. sendCloseStream waits for the final results. close() or an aborted abortSignal (a connect() option, so it fits your AbortController) stops at once and drops whatever is pending.
  • Hidden reconnects. The socket reconnects up to 30 times by default after an unexpected close. That doesn't apply to a 401, which fails at once. Audio sent during the gap is lost and timestamps restart, so set reconnectAttempts: 0 if you'd rather handle it yourself.

If turn-taking comes up: Flux (listen.v2.connect({ model: "flux-general-en", ... })) is Deepgram's model built for voice agents. Instead of is_final and speech_final, it sends TurnInfo events: StartOfTurn, EagerEndOfTurn (start the LLM early), TurnResumed (throw that draft away) and EndOfTurn. It works best with 80 ms chunks.

4. ElevenLabs streaming text-to-speech 2.5 min

Package @elevenlabs/elevenlabs-js 2.70. This is the HTTP streaming endpoint from the brief's link. Audio arrives as the voice is generated, so playback can start before generation ends.

import { ElevenLabsClient } from "@elevenlabs/elevenlabs-js";

const elevenlabs = new ElevenLabsClient({ apiKey: process.env.ELEVENLABS_API_KEY });
const audio = await elevenlabs.textToSpeech.stream(
    "JBFqnCBsd6RMkjVDRZzb",                  // voice id ("George", a default voice)
    { text, modelId: "eleven_flash_v2_5", outputFormat: "pcm_24000" },
    { abortSignal: controller.signal },      // per-request options
);
for await (const chunk of audio) player.stdin.write(chunk);   // play while downloading

Measured on your machine (Flash, PCM): the first audio arrived 0.51 s after the request, on a cold connection that includes TLS setup. The whole 3.3 s sentence had arrived by 0.63 s, so generation runs about 5 times faster than playback. Time to first byte is the number that matters.

TransportHTTP stream (above), or the WebSocket /stream-inputHTTP per sentence. The WebSocket when you feed LLM tokens directly.
  • Interrupting playback. The SDK's play() and stream() are fine for demos, but you can't stop them mid-sentence. tts.ts spawns ffplay itself, so barge-in is controller.abort() plus player.kill(). Ctrl+C does exactly that.
  • Built-in retries. The SDK retries 408, 429 and 5xx responses twice, waiting 1 s then 2 s, and it honours a Retry-After header of up to 60 s. On a live call, silence is worse than an error, so consider maxRetries: 0 and speaking a fallback line. This links straight to the "add retry with backoff" question.
  • Errors. Failures throw an ElevenLabsError with statusCode and body.detail.status, for example "invalid_api_key". I checked this against the real API with a placeholder key.

WebSocket input streaming (not wrapped by the JS SDK, so you'd use the ws package; not tried here):

wss://api.elevenlabs.io/v1/text-to-speech/{voice_id}/stream-input?model_id=eleven_flash_v2_5
// header xi-api-key: ...
→ {"text": " "}                               // first message opens the stream
→ {"text": "The weather in Tokyo "}           // LLM deltas, each ending in a space
→ {"text": "is sunny. ", "flush": true}       // end of the turn: generate now
→ {"text": ""}                                // close
← {"audio": "<base64>", "alignment": {...}} ... {"isFinal": true}

The server buffers text until about 120, 160, 250 or 290 characters (chunk_length_schedule) unless you flush, and it closes after 20 s without input.

5. Plugging it into your CLI 1.5 min

The likely pairing direction is "add real-time audio input (we'll provide the STT integration)". Here's how each piece maps onto your code:

  • Input. Replace getUserInput() with "wait for the next utterance": a Promise that resolves on speech_final or UtteranceEnd with the buffered is_final text. The rest of main() stays the same.
  • Output. callLlm() already yields text deltas. Buffer them up to a sentence boundary, send each sentence to textToSpeech.stream, and play the sentences in order. Sentence by sentence keeps the first audio early.
  • Cancellation. Reuse the per-turn AbortController. Pass its signal to the TTS request and kill ffplay when it aborts. A SpeechStarted while the agent is talking becomes your Ctrl+C: barge-in is controller.abort().
  • Pending state. A spinner doesn't work on a phone call. During the 3 to 8 s research call, speak a filler line such as "Let me look that up."
  • Echo. With speakers instead of headphones, the mic hears the agent. Either ignore transcripts while it speaks (and send KeepAlive) or rely on headphones for the demo.

From the end of the user's speech to the first audio is usually 1 to 2 s. The biggest levers are end-of-speech detection and the LLM's first token. What keeps the total low is streaming at every stage: no stage waits for the previous one to finish.

7. 100 concurrent calls 1 min

  • Cost per call: one Deepgram socket, one LLM stream, and one TTS request per sentence. That's all network waiting, so a few Node processes can handle 100 calls. Don't run ffmpeg per call: phone audio (for example Twilio) is already μ-law 8 kHz, which Deepgram accepts (encoding: "mulaw", sample_rate: 8000) and ElevenLabs can output (ulaw_8000).
  • What breaks first: provider concurrency caps. ElevenLabs Flash allows 4 concurrent requests on Free and 30 on Business. Deepgram streaming STT allows up to 150 on pay-as-you-go. After those come LLM rate limits.
  • What to monitor, per turn: STT lag, LLM time to first token, TTS time to first byte, and end of speech to first audio (p50 and p95). Also socket closes and reconnects, 429s, and concurrency in use versus each cap.
  • Failure modes: the STT socket drops mid-call (reconnect; timestamps restart at 0), a TTS 429 (queue or fall back), a slow tool (filler speech), the caller interrupts (abort and clear the audio queue).

8. Run it 30 s

npm run stt                          # ffmpeg speaks a test sentence, Deepgram transcribes it
npm run stt -- mic                   # first microphone ffmpeg lists
npm run stt -- path/or/url.mp3       # any file or URL ffmpeg can read
npm run tts -- "Hello from Elyos"    # streams and plays it; Ctrl+C interrupts
